## Who can change the Hall right now?

On Solana, a program's code can be replaced only by its upgrade authority: one
key, recorded on chain next to the program. That key is what Seametry calls the
Key. While someone holds it, the program can be changed. Once it is set to
none, the program can never change again, by anyone, including Seametry.

In practice: while the Key exists, the rules you checked today can be
different tomorrow. Once it is set to none, the code you checked is the code
that runs, permanently.

## What can the holder of the Key do, and what can't they?

The holder can replace the program's code. Nobody else can, and once the Key is
thrown away, nobody can at all. Try both sides of that rule:

That is why the Key matters more than any promise about behaviour. A promise
can be broken by the next version of the code. A program with no upgrade
authority has no next version.

## What must the final Hall preserve?

Three guarantees. Every design decision in the Hall exists to make them literally
true, and the final program must carry all three.

**The melt always works. Delivery is each issuer's.** Burning shares for a
claim on the constituents can never be blocked by anyone. Delivering each
constituent is subject to that constituent's issuer, and the Hall says so rather
than pretending otherwise.

In practice: if an issuer freezes one stock, you can still Melt. The frozen
stock stays yours as a named Claim, and the others are delivered. You can try it
on [How it works](/docs/how-it-works#what-happens-when-i-melt-and-what-if-an-issuer-freezes-one-constituent).

**The Hall adds no prerogatives of its own.** The share mint has no freeze
authority, no permanent delegate, no pause, no hook. No instruction lets anyone
alter a formula, move a holder's assets, or stop a melt.

In practice: the issuers of the stocks inside an Alloy keep their powers, and
the Hall states them. The Hall itself adds none on top, so an Alloy share can
never be frozen or taken by the Hall.

**The Hall never needs a price.** Strike and melt move quantities. No oracle, no
quote, no NAV is an input to any instruction. Price manipulation cannot touch
minting, and the Hall keeps working when every price source is down.

In practice: a Strike of 10 shares costs the same quantities whether prices are
calm, moving fast, or unavailable.

Which instructions move constituents, and which only keep records:

```text
instruction   what it does                                     moves a constituent
create        pulls exactly the required units, mints shares   yes, every leg, in
redeem        burns shares, credits a Claim on every leg       no
withdraw      delivers one leg of a Claim                      yes, that one leg, out
sync          reconciles one leg's records with its balance    no, reads only
```

Because `redeem` moves no constituent, a freeze, a pause or a transfer hook,
which all act on transfers, has nothing to stop. That is the first guarantee,
built into the instruction rather than promised beside it.

<ClaimLine lead="The Hall reads quantities.">Strike and Melt do not use an oracle, a quote or NAV as an instruction input.</ClaimLine>

## What does "final" mean, if the Hall still needs to improve?

An upgrade path is an admin key with a better name. So the Hall never upgrades
in place. Each version is its own program, made final once. Improving the Hall
means deploying a new version beside the old one. The old Hall keeps working for
whoever stays, and anyone can move across, because Melting is always open.

## Why is the Key not thrown away today?

Because the Hall is still on devnet, a test network, and still being built.
Throwing the Key away fixes the code forever, so it happens once, on the mainnet
Hall, after a program audit and a legal read. When it happens, this page will
show the transaction that did it, and the panel at the top will read the
authority as none.
