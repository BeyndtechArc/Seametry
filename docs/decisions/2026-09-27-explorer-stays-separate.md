# The Explorer stays its own static site, off Vercel, on Cloudflare Pages

**Decision record. Historical, append only, not a living document.**
Recorded 27 September 2026.

The living authorities are `../SERVICE_CATALOG.md` section 4 for hosting and
`../prd/EXPLORER.md` for what changed in the Explorer's own scope.

---

## Context

`decisions/2026-09-27-web-app-and-payments.md` D1 put the Explorer, the
Terminal and the business pages in one Next.js app, `clients/web`. Phase 4 of
scaffolding that app (security headers, proven with a real Chromium test
rather than assumed) found this does not hold: the Explorer's own
requirement, `script-src 'self'` with nothing else, is `EXPLORER.md` section
8's requirement for the verification ritual's trust claim, and Next's App
Router always emits an inline hydration script no page can opt out of.
`experimental.sri` covers external `<script src>` chunks only; the inline
script stays unaddressed, confirmed by a Playwright test loading the built
app in headless Chromium: two real `securitypolicyviolation` events,
`script-src-elem: inline`, both against the inline React Server Components
payload, not against anything this repository wrote.

Storm asked whether this could just be solved by keeping the Explorer
static, separately, rather than forcing the whole app to choose between
weakening the policy or paying for a nonce on every request.

## Decisions

**D1. The Explorer is not part of `clients/web`.** It stays what it already
is: static HTML generated by `server/cmd/explorer`, unchanged in shape,
deployed on its own. This reverses `2026-09-27-web-app-and-payments.md` D1
for the Explorer specifically; that record's D2 through D6, the publish step,
the business pages' ownership, Vercel, Fly, and x402, all still hold.

**D2. The Explorer deploys to Cloudflare Pages, not Vercel.** Checked
27 September 2026: Cloudflare Pages Free gives unlimited sites and
bandwidth with no commercial-use restriction, and a plain static site (no
framework runtime, one external script for verification) carries none of
the risk a Next.js deployment there would: no experimental middleware
support to depend on, no Workers bundle size ceiling to hit. This is a
better fit than Vercel for this specific artifact, not a downgrade from it;
Vercel Hobby's non-commercial restriction, a live concern for `clients/web`,
never needs weighing here at all.

**D3. `clients/web` (the Terminal and the business pages) keeps Vercel,
and resolves its own CSP with a per-request nonce, not by weakening the
policy.** This app was never a candidate for static generation regardless
of the Explorer question: wallet connections, signed-in state and live data
all need a request in hand. So there is no static-generation benefit being
traded away by choosing nonces, unlike what weighing (a) `'unsafe-inline'`
against (b) nonces would have implied if the Explorer's constraint had
still applied here. `proxy.ts` generates a fresh nonce per request; every
route calls `connection()` to force dynamic rendering, without which the
nonce would be baked into a statically prerendered page and reused on every
request, which is not a nonce. Proven the same way the violation was found:
the same Playwright test, rerun against the nonce-based policy, reports
zero violations, and two consecutive requests are asserted to carry
different nonces.

**D4. Cloudflare fronts both, as DNS and CDN, regardless of where either
runs.** Proxying (the orange cloud) to a non-Cloudflare origin is ordinary,
documented Cloudflare behaviour, unaffected by which of Vercel or Cloudflare
Pages sits behind it.

## What this costs

A `proxy.ts` file placed at the project root does nothing silently: Next's
own convention is that it must live inside `src/` when the app uses a `src`
directory, which this one does. The first build showed no evidence it had
registered at all (no `Proxy (Middleware)` line in the build output, and a
direct `curl` of the running server carried none of the configured headers)
until it was moved there.

Two separately hosted sites means two deploy pipelines, two domains to
configure, and no shared session between them, which is fine, since nothing
about the Explorer needs a session in the first place.

## What this does not settle

Which subdomain or path carries the Explorer (`explorer.seametry.xyz` was
Storm's suggestion, not yet decided against alternatives). The API's own
domain, already open in `prd/API.md` section 14.
