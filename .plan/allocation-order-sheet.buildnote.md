Surface
Allocation basket builder in the App shell, plus a shared modal sheet registered in the Pattern Register.

Template
Mobile Order sheet adapted into a desktop builder with a persistent end rail and a mobile occluding sheet.

Question
What will this coordinated plan buy, where will each token arrive, and what remains before the next purchase can be signed?

Sections
1. Page header and bounded execution terms.
2. Basket amount, before the long evidence inventory.
3. Constituent selection with condition reports available on demand.
4. Per-constituent purchase previews and settlement states.
5. Persistent desktop order sheet; mobile trigger and occluding modal sheet.

Components
Existing: Page header, Network badge, Field, Stamp, Grade, Condition report, Quote block, Quiet action, Key, Rule.
New: Modal sheet, isolated in its own client entrypoint so the server-capable shared component package remains server-safe.

Data
Captured policy admissions, issuer prerogatives, evidence slot and age, USDC input, even per-constituent split, wallet session, Jupiter quote and simulation response, transaction state and signature. Fixture data remains labelled on the Pattern Register only.

States
Builder: unavailable, empty selection, invalid amount, ready to preview, preparing, prepared, signing, sending, settled, failed. Modal sheet: closed and open; its caller owns loading, empty, stale, unavailable and error content.

Ceremony
The approval Key is the only custody-changing ceremony. The sheet motion answers an explicit review action and lands instantly for reduced motion.

Names
Operational labels lead: Build a basket, Order sheet, Preview purchase, Approve and sign. Allocation remains the world term beneath the operational work.

Assumptions
The right order sheet is persistent at wide widths and becomes an end sheet below the desktop breakpoint. Configuration names stay out of visitor-facing copy. Eligibility remains fail-closed until the production country policy is supplied.
